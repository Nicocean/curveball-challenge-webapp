Schritt 1 von 7 · Verständnis

Das Zielzertifikat

Schau die Zeile direkt unter Public Key Algorithm im Auszug an. Steht dort nur eine Kennnummer wie prime256v1, ist das eine benannte Kurve: die Domain-Parameter (p, a, b, G, n, h) stehen nicht im Zertifikat, sondern werden aus einer Tabelle nachgeschlagen. Stünde stattdessen ein Block mit allen sechs Werten ausgeschrieben, wären die Parameter explizit. → Genau dieser Unterschied ist die Angriffs-Lücke.

Bevor wir angreifen, schauen wir uns das Ziel an: das echte Zwischenzertifikat der COMODO ECC Extended Validation Secure Server CA. Es gehört zum vertrauten Wurzelspeicher — und genau diese CA-Rolle wird der Angriff später vortäuschen.

Nichts ausführen — unten steht der relevante Auszug aus openssl x509 -in comodo-intermediate.crt -text -noout, den wir dir vorbereitet haben. Lies ihn und beantworte die Frage darunter.

Public Key Algorithm: id-ecPublicKey ASN1 OID: prime256v1 NIST CURVE: P-256 pub: 04:57:70:1a:3f:... ← öffentlicher Punkt Q X509v3 Basic Constraints: critical CA:TRUE ← darf weitere Zertifikate ausstellen

Schritt 2 von 7 · Verständnis

Die Idee

Lies den Code Zeile für Zeile: inverse_mod liefert k⁻¹, dann wird der Punkt Q aus den Koordinaten zusammengesetzt, und schließlich wird Q mit k⁻¹ multipliziert. Genau die Reihenfolge der Formel.

Kein Terminal — nur Verstehen. Der Angreifer kennt den privaten Schlüssel d der echten CA nicht. Der Trick: statt d zu bestimmen, wählt er einen eigenen Skalar k und baut sich einen manipulierten Generator G' passend dazu. Weil k · G' = k · k⁻¹ · Q = Q, funktioniert k als privater Schlüssel relativ zu G' — der öffentliche Punkt Q bleibt derselbe wie bei der echten CA. Ordne jede Zeile aus get_exploit_generator() ihrem Teil der Formel zu.

Code (badecparams.py)

def get_exploit_generator(k, Qx, Qy, curve): k_inverse = inverse_mod(k, curve.order) Q = Point(curve.curve, Qx, Qy, curve.order) G = Q * k_inverse return (G.x(), G.y())

Formel

G' = k⁻¹ · Q

d = privater Schlüssel der echten CA (unbekannt).
k = frei gewählter Skalar des Angreifers.
Weil k · G' = k · k⁻¹ · Q = Q, ist k ein gültiger privater Schlüssel relativ zum manipulierten Generator G' — ohne den echten Schlüssel d zu kennen.

Mit dem manipulierten Generator G' ist die Signatur mathematisch korrekt; mit dem echten Generator G schlägt sie fehl — genau das ist der Effekt des Patches.

Schritt 3 von 7 · Praxis

Der Angriff

Ohne k kannst du G' nicht berechnen. Ohne die Original-Kette kennst du Q nicht. Und ohne G' lässt sich das gefälschte Zwischenzertifikat nicht signieren. Am Ende brauchst du die Endzertifikate für den TLS-Handshake.

Jetzt wird die Waffe gebaut. badecparams.py lädt die Original-Kette, extrahiert Q aus dem Zwischenzertifikat der COMODO ECC EV CA, wählt ein k, berechnet G' = k⁻¹ · Q, ersetzt die Domain-Parameter durch explizite Werte mit G' als Generator und signiert damit anschließend die drei Endzertifikate.

✅ badecparams.py und comodoecccertificationauthority-ev-comodoca-com-chain.pem liegen bereits im Repo-Ordner aus Schritt 0.
Vorbedingung: Beide Dateien oben liegen im Angriffsordner. Virtuelle Umgebung ist aktiv (source .venv/bin/activate).
Aufruf: keine Argumente nötig — die Chain-Datei wird über einen festen Dateinamen aus dem Arbeitsverzeichnis geladen.
./badecparams.py

Nach ein paar Sekunden liegen acht neue Dateien im Ordner — aufgeteilt in drei Blöcke:

## Gefälschte Zertifizierungsstelle (Schritt 4) intermediateCA.crt # Original + gefälschtes Zwischenzertifikat (zwei PEM-Blöcke) intermediateCA.key # Angreifer-Schlüssel: k als privater Skalar zu G' ## Code-Signing-Paket (Schritt 5) authenticode.crt # Endzertifikat für Code-Signing authenticode.key # dazugehöriger Schlüssel authenticode.spc # signtool-Paket (PKCS#7-Zertifikatscontainer) authenticode.pvk # signtool-Privatschlüssel ## TLS-Endzertifikat (Schritt 6 & 7) localhost.crt # Endzertifikat für TLS (nsa.gov, microsoft.com, PayPal-Subject) localhost.key # dazugehöriger Schlüssel

Sanity-Check: ls -la intermediateCA.crt authenticode.spc localhost.crt — alle drei müssen existieren und > 0 Byte sein.

Schritt 4 von 7 · Praxis

Die gefälschte CA

openssl x509 -text -noout zeigt die interpretierte Ansicht: wenn p, a, b und n zu prime256v1 passen, druckt es einfach diesen Namen aus — der Generator G wird dabei gar nicht überprüft oder angezeigt. Um den manipulierten Generator zu sehen, müsste man openssl asn1parse nehmen oder die Roh-Bytes vergleichen. Genau diese Blindstelle in Standard-Tools ist der Kern von CVE-2020-0601.

Aus Schritt 3 ist die Datei intermediateCA.crt entstanden — sie enthält zwei PEM-Blöcke: oben das gefälschte Zwischenzertifikat, unten das echte (unverändert). Beide werden später gemeinsam über die Leitung ausgeliefert.

Führe den Command unten in deinem Terminal aus und vergleiche deinen Output mit dem Referenz-Auszug aus Schritt 1 darunter. Achte auf jede Zeile — Subject, Issuer, Public Key, Extensions.

Vorbedingung: Schritt 3 wurde ausgeführt, intermediateCA.crt existiert.
openssl x509 -in intermediateCA.crt -text -noout

Referenz-Auszug aus Schritt 1 (echtes CA-Zert):

Public Key Algorithm: id-ecPublicKey Public-Key: (256 bit) pub: 04:57:70:1a:3f:... ← öffentlicher Punkt Q ASN1 OID: prime256v1 NIST CURVE: P-256 X509v3 Basic Constraints: critical CA:TRUE ← darf weitere Zertifikate ausstellen

Schritt 5 von 7 · Praxis

Codesignatur

Ein reguläres Code-Signing-Zertifikat wäre von einer echten Code-Signing-CA ausgestellt (z.B. COMODO Code Signing CA). Schau dir in deinem Output die oberste subject=-Zeile an: der Common Name verrät sofort, ob das ein normales Zert oder etwas Anderes ist. Und dann die issuer=-Zeile direkt darunter — wer hat das unterschrieben?

Neben dem TLS-Endzertifikat aus Schritt 3 wurde parallel ein Authenticode-Paket erzeugt — das sind die Dateien authenticode.spc und authenticode.pvk. Sie sind das Windows-Format für Code-Signing mit signtool. Auf einem ungepatchten System ließe sich damit eine ausführbare Datei signieren, die Windows als vertrauenswürdig einstuft.

Der Command unten listet alle Zertifikate, die in der SPC-Datei stecken. Führe ihn aus und vergleiche deinen Terminal-Output mit der Referenz darunter — so würde eine echte Code-Signing-Kette aussehen.

Vorbedingung: Schritt 3 wurde ausgeführt, authenticode.spc existiert.
openssl pkcs7 -inform DER -in authenticode.spc -print_certs -noout

So sähe eine offizielle Code-Signing-Kette aus (Referenz, kein Angriff):

subject=... CN=<Firmenname> Code Signing # Software-Hersteller issuer =... CN=COMODO Code Signing CA # offizieller Aussteller subject=... CN=COMODO Code Signing CA # Zwischen-CA issuer =... CN=COMODO Certification Authority # Comodo-Root subject=... CN=COMODO Certification Authority # Root, selbstsigniert issuer =... CN=COMODO Certification Authority

Vergleiche das mit deinem eigenen Output — was steht dort in der obersten Zeile?

Schritt 6 von 7 · Praxis

Das EV-Zertifikat

Der grüne EV-Balken (Extended Validation) wurde von Browsern wie Chrome, Firefox und Internet Explorer bis ca. 2019 in der Adressleiste angezeigt, wenn zwei Bedingungen zutrafen: (1) das Endzertifikat trägt eine bekannte EV-Policy-OID (jede CA hat eine eigene, hartcodiert im Browser) und (2) die Kette endet bei einer als EV-fähig gelisteten Zertifizierungsstelle. War beides erfüllt, zeigte der Browser den Firmennamen aus dem Subject grün hinterlegt neben dem Schloss an — z.B. „PayPal, Inc. [US]“. Ein besonders starkes Vertrauens-Signal.

Der Angriff wäre technisch schon überzeugend, wenn nur das gewöhnliche Schloss-Symbol erscheinen würde. Aber der Trick geht weiter: localhost.crt — das TLS-Endzertifikat für Schritt 7 — wurde gezielt so gebaut, dass ein ungepatchter Windows-Browser sogar den grünen EV-Balken mit „PayPal, Inc.“ daneben anzeigt.

Zwei Zutaten machen das möglich:

  • Der Subject-Name lautet absichtlich O=PayPal, Inc. — das ist der Text, den der Browser später im grünen Balken anzeigt.
  • Das Zertifikat trägt die Extended-Validation-Policy-OID 1.3.6.1.4.1.6449.1.2.1.5.1 — die offizielle EV-Kennung von Comodo. Windows kennt diese OID und hält die Kette für EV, weil er sie – dank CurveBall – auf die (gefälschte) Comodo-CA zurückführt.

Zum Vollpaket gehört: das Zertifikat gilt zusätzlich für nsa.gov, www.nsa.gov, microsoft.com, www.microsoft.com und localhost — alle als Subject Alternative Names eingetragen. Damit ließe sich der TLS-Handshake später unter jedem dieser Namen führen.

Vorbedingung: Schritt 3 wurde ausgeführt, localhost.crt existiert.
Ziel: bestätige, dass die zwei EV-Zutaten (Subject-Name, EV-Policy-OID) tatsächlich im Zertifikat stehen.
openssl x509 -in localhost.crt -text -noout

Die relevanten Zeilen im Output:

Subject: ... O=PayPal, Inc. ... # Firmenname für Balken X509v3 Subject Alternative Name: DNS:localhost, DNS:nsa.gov, DNS:www.nsa.gov, DNS:microsoft.com, DNS:www.microsoft.com X509v3 Certificate Policies: Policy: 1.3.6.1.4.1.6449.1.2.1.5.1 # COMODO EV-Policy-OID

Schritt 7 von 7 · Praxis · Finale

Über die Leitung

Zwei Faktoren müssen zusammenkommen: der Verifier muss den Generator aus dem Zertifikat übernehmen und das Zertifikat muss denselben öffentlichen Punkt Q tragen wie eine bereits vertraute Zertifizierungsstelle im Zwischenspeicher. Fehlt eins von beiden, greift der Trick nicht.

Das Angriffsmaterial liegt bisher nur auf der Platte. Der letzte Schritt liefert es über HTTPS aus. httpd.py ist ein winziger Python-TLS-Server, der auf Port 8443 lauscht und die gefälschte Zertifikatskette per Handshake ausliefert. Als Argument braucht er den Pfad zum Schlüssel und liest daneben liegend localhost.crt und intermediateCA.crt ein.

✅ httpd.py liegt bereits im Repo-Ordner aus Schritt 0.
Vorbedingung: Schritt 3 wurde ausgeführt. localhost.key, localhost.crt und intermediateCA.crt liegen im aktuellen Ordner.
Terminal 1 — Server starten:
python3 httpd.py localhost.key

Der Server bindet sich auf 0.0.0.0:8443 und wartet auf Verbindungen. Läuft im Vordergrund — Konsole offen lassen, mit Ctrl+C beenden. Port 8443 ist unprivilegiert, es sind keine sudo-Rechte nötig.

Terminal 2 — Handshake auslösen:
openssl s_client -connect localhost:8443 -showcerts

Der Handshake zeigt drei Zertifikate übereinander:
  0 s:CN=PayPal, Inc. ... — das gefälschte Endzertifikat,
  1 s:CN=COMODO ECC Extended Validation ... — die gefälschte CA (mit expliziten Parametern und G'),
  2 s:CN=COMODO ECC Extended Validation ... — dasselbe Zwischenzertifikat, diesmal echt (mit benannter Kurve).
Ein ungepatchter Windows-Client würde diese Kette akzeptieren, weil sein Zwischenspeicher-Vergleich nur Q und Seriennummer prüft — die Domain-Parameter kommen aus dem gerade eingelieferten Zertifikat.
